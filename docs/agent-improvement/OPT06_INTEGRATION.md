## 2. 작업본 모델 (DB 마이그레이션 없음)

- 저장 위치: `ideal_schedule_runs.summary.workingCopy` = `{ editLog, evaluation, readiness }`(jsonb). 새 테이블·열 없음.
- **수정 이력**(`editLog.ts`): 항목마다 수정 전·후 블록 상태 전체(`EDIT_COLUMNS` 31열)를 저장해 정확히 복원. `entries[0..cursor)`가 적용됨. `seq`는 실행 취소·다시 실행 포함 모든 변경마다 오른다. 수정 개수는 제한하지 않는다 — 이력 저장 크기 보호로 120건에서 새 수정을 *거부하고 안내*(조용히 버리지 않음).
- **상태** 3가지(`planVersion.ts`): `COMPUTED` 계산 완료본 / `DIRTY` 수정 후 재평가 전 / `REEVALUATED` 수정 후 재평가됨. DIRTY에서는 비교 카드를 만들지 않고, 수정 직후 화면이 한 번 자동으로 재평가한다(실패하면 되풀이하지 않고 [재평가] 버튼 유지).
- **재평가가 보존·갱신하는 것**: 보존 — 교체 때 붙은 근거(`MANUAL_SEARCH`·`RIGHTS_AT_SWAP`), 필수·잠금 규칙 칸(패널티 없는 고정), 경쟁 Benchmark·장르 원형 칸의 저장 값. 갱신 — 인접 편성·같은 시간 반복·하루/주 반복 노출·그날 장르 편중·주간 합계. **하지 않는 것** — 다른 칸을 바꾸는 탐색, 등위·유지/교체 판단 건수 갱신(→ [다시 계산]).
- **[다시 계산]** 은 새 실행을 만든다. 이 작업본은 그대로 남는다. 수동 변경 유지를 고르면 직접 교체·직접 잠금·필수 규칙을 제약으로 이어받고 수정 이력·재평가 값은 이어받지 않는다.
- **동시 수정**: 화면이 마지막으로 본 `editSeq`(`baseSeq`)가 서버와 다르면 거부(덮어쓰지 않음). **거의 동시에 들어온 두 요청은 막지 못한다**(DB에 버전 열이 없다 — 열 추가는 별도 승인).
- **실패 시 보존**: 교체·잠금·실행 취소는 이력 저장이 실패하면 블록을 수정 전 상태로 되돌린다. 재평가·비교·검사 실패는 편성안을 바꾸지 않는다.

## 3. 권리 판정 규칙 (`slotRights.ts`, `rightsServer.ts`)

- `unavailable` → 교체 거부. `conditional`·`unknown`·`not_checked` → 교체는 되지만 **검토안**(실행 가능 표시 금지). `available`만 실행 가능.
- Avail 자료가 없거나 판정이 실패하면 "확인하지 못함"이지 "가능"이 아니다. 경쟁 Benchmark·장르 원형은 판정 대상이 아니라 `not_checked`.
- 판정 함수는 엔진 게이트와 같은 `evaluateEligibility`. 조회만 하며 권리 예약·원장 기록·편성 저장은 하지 않는다.
- 후보 목록(`GET …/blocks/[blockId]`)에 후보별 권리·교체 가능 여부가 붙는다.

## 4. 비교 카드·주요 변경 (`planCards.ts`, `topChanges.ts`, `variantsServer.ts`)

- 카드 규격: 주간 기대, 기준안 대비 %p·%, 변경 칸·분, 반복 편성, 필수 충족, 하드 제약 위반, 권리 확인율·소진, 근거 부족 비중, 기준안보다 낮은 칸(하방), 검증 오차 시나리오(있을 때).
- 기준안 = 저장된 CURRENT 층(지난주 실제 편성), 성과우선안 = 지금 편성안. **네 안 모두 같은 모델·같은 기준일·같은 제약으로 다시 평가**한다.
- 최소변경·균형안 = 기준안에서 성과우선안 쪽으로 칸을 하나씩 바꾼 효율 경계의 점. **칸 구조가 같을 때만** 만든다("AI 시간 최적화" 실행은 만들 수 없고 이유를 표시). 변경 14칸 이하면 탐욕 전진, 넘으면 칸별 단독 효과 순(거친 근사 — 화면에 표시).
- "최고 기대안" 표지는 기준안보다 오른 안 중 기대 차이가 가장 큰 안에만. **"최적 증명"은 어떤 카드에도 없다.**
- 주요 변경 5건은 *주간 기여*(차이 × 분 ÷ 평가 분) 순. 슬롯 %는 기준값이 작거나(주간 평균의 25% 미만) |%|>300%면 숨기고 모든 항목에 "한 칸의 상대 차이일 뿐 주간 실제 성공 확률이 아닙니다"를 붙인다. 필수·잠금·수동 변경은 칩으로 표시(규칙이 정한 변경이지 모델이 고른 개선이 아님).
- 기준안과의 짝짓기는 화면 대조표와 같은 겹침 기준.

## 5. 확정 준비 검사 (`readiness.ts`, `readinessServer.ts`, `POST …/readiness`)

8개 항목: 버전·동시 수정 / 재평가 현재성 / 최신 Avail 재판정 / 공유 잔여 횟수 / 회차 길이 / 하드 제약 / 필수 편성 / 권리 목록 버전. 결과 `EXECUTABLE`·`REVIEW_ONLY`·`BLOCKED`.
- 읽기 전용: `operationApplied: false` 고정. 외부 시스템 반영·권리 예약 없음. `record: true`일 때만 검사 요약을 작업본에 남긴다("검토안으로 저장").
- 필수 편성을 최신 설정으로 *다시 확인하지 못하면* 통과로 세지 않고 검토안으로만 둔다.
- 권한: `schedule_finalize`(PD 가능). 수정 API는 `schedule_edit`(PD 가능). 둘 다 `permissions.ts`에서만 판정한다.
- 반복 한도는 "설정 한도 또는 엔진이 받아들인 원래 계산안이 쓴 횟수 중 큰 값"으로 본다(`capOverrideFrom`) — 엔진은 오리지널 드라마·예능의 한도를 12주 관측 최대치로 늘려 계산하므로, 늘어난 반복만 위반으로 본다.

## 8. 실데이터 확인에서 드러난 사실 (숨기지 않는다)

1. 이 실행(2026-10-06 생성, 모델 버전 기록 이전)은 **다시 평가한 주간 기대 0.5094, 저장 값 0.5211**(−0.0117). 같은 편성안인데 현재 모델과 계산 당시 모델·자료가 달라서다. 그래서 재평가는 계산 완료본도 같은 모델로 다시 평가해 `저장 값 → 재평가 값 → 수정 후`를 함께 보여 주고(**수정의 효과는 재평가 값 기준**), 비교 카드는 차이를 상단에 표시한다. 모델 버전이 기록된 최신 실행에서는 차이가 없어야 한다(확인 필요).
2. 제 검사가 반복 한도를 기준안 횟수로만 봐서 거짓 위반 9건이 나왔고, 엔진이 받아들인 계산안의 횟수를 허용치로 쓰도록 고쳤다(위반 0건).
3. 이 환경에서는 Avail 자료가 없어 모든 칸이 "권리 확인 안 함 → 검토" 상태다 — 권리가 실제로 들어간 뒤의 화면은 합성 테스트로만 확인했다.

## 9. 남은 한계

- 모든 수치는 합성 또는 이 한 실행의 읽기 전용 확인이다. 실제 Avail 입력 후 확정 준비 검사의 통과·소진 표시는 미확인.
- 거의 동시에 들어온 두 요청은 막지 못한다(버전 열 필요 — 승인 사항).
- 최소변경·균형안은 칸 구조가 같을 때만 만들 수 있다.
- 경쟁 Benchmark·장르 원형 후보는 재평가하지 않는다(저장 값 유지).
- 확정 뒤 *실제 운영 반영*은 구현하지 않았다(검사는 읽기 전용, 외부 시스템 연동은 범위 밖).
- 근거 패널의 "유사 방송 이력·긴 제목·특집·다른 시즌 식별"은 이번에 새로 만들지 않았다(기존 블록 상세의 근거·후보 비교·권리 사유·되돌리기는 연결됨).
- 채택 기록 저장소(OPT05)·마이그레이션 20261011~14·OPT04 작업 큐 테이블은 승인 대기.
