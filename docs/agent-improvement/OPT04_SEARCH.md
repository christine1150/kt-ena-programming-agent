**바꾼 것(모두 결과가 같은 속도 개선)**

4. 프로그램·장르 묶음을 정수 id로 바꿔 매 호출의 문자열 연결을 없앴다.

**차분 평가가 전체 재평가와 같다는 확인(T07)** — 검증 모드(`search.verifyDelta`)는 차분 평가마다 전체 재평가와 비교해 불일치를 센다. 합성 세계에서 KEEP·장르 없음 5,362건, KEEP·장르 있음(장르 편중·상위 묶음 경로) 1,643건, AI·장르 있음 9,890건을 비교해 **불일치 0건, 최대 차이 1e-9 이하**. 검증 모드는 평가가 늘어 느리므로 시험·점검용이다.

## 2. 탐색 방법 비교 — 무엇을 채택하고 무엇을 보류했나

정답(완전탐색)을 아는 소형 문제(슬롯 7·후보 5, 연속 가산·권리 불가·프로그램 한도·잠금 포함) 100개 × 4종(separable·adjacent·capped·locked), 해 없는 14건 제외 386개. `npm run opt04:methods`로 재현한다. **연속 가산(앞 편성이 특정 후보일 때 뒤 후보가 좋아지는 짝)은 방법 간 차이를 보이려고 일부러 크게 넣은 합성 구조**라, 실제 엔진에서의 크기는 다르다.

| 방법 | 유효 해 | 정답 도달률 | 평균 격차 | 최악 격차 | 평균 점수 계산 횟수 |
|---|---|---|---|---|---|
| 탐욕 구성만 | 100% | 54.7% | 3.00% | 31.1% | 28 |
| 탐욕 + 교체 | 100% | 59.8% | 2.01% | 24.4% | 54 |
| **탐욕 + 교체 + 맞교환(현재 엔진과 같은 이웃)** | 100% | 78.8% | 0.68% | 24.1% | 72 |
| 다중 시작 8회(시드 고정) + 교체·맞교환 | 100% | 94.6% | 0.07% | 3.5% | 647 |
| 빔 탐색 폭 3 | 100% | 69.4% | 1.14% | 14.7% | 76 |
| 빔 탐색 폭 10 | 100% | 86.0% | 0.44% | 10.6% | 220 |

판단
- **현재 이웃(탐욕+교체+맞교환) 유지.** 맞교환이 정답 도달률을 59.8% → 78.8%로 올리므로 빼지 않는다.
- **다중 시작(8회)은 정확도가 가장 좋지만(정답 도달 94.6%, 최악 격차 3.5%) 평가가 9배 든다.** 지금 엔진에 넣지 않은 이유 ① 이 격차는 이웃 가산을 크게 넣은 합성 문제의 값이며 실제 엔진 목적함수의 상호작용 크기는 실데이터로 확인하기 전이다 ② 기존 틀 유지 모드가 합성 세계에서 7초라 ×8은 시간 예산 안에 들지 않는다(예산이 있으면 "시간 되는 만큼 시작 횟수를 늘리는" 방식이 가능) ③ 시작마다 시드가 필요하므로 시드를 입력 지문에 넣는 설계가 먼저다. **채택 조건:** 실데이터에서 연속·같은 시 상호작용이 목적함수에서 차지하는 비중을 재서 정답 격차가 의미 있게 클 때, 시간 예산이 있는 환경에서.
- **빔 탐색(폭 10)** 은 현재 이웃보다 정답 도달률이 조금 높지만(86.0% vs 78.8%) 평가가 3배이고 다중 시작보다 낮다. 엔진의 평가값은 앞 편성·같은 시 반복·그날 장르 비중에 전역으로 의존해 "부분 편성 점수로 순위를 매기는" 빔이 부정확해지므로 보류.
- **웜 스타트(지난주 편성에서 시작)** — 합성 세계 3개 측정(탐색 직후 목적함수, 교체 횟수, 시간):

  | 세계 | 탐욕 시작 | 지난주 편성 시작 |
  |---|---|---|
  | 1 | 584.08 · 82회 · 7.0초 | 583.96 · 556회 · 7.4초 |
  | 2 | 609.84 · 59회 · 6.1초 | 609.69 · 504회 · 9.1초 |
  | 3 | 567.51 · 43회 · 5.6초 | 567.50 · 459회 · 6.1초 |

  속도 이득이 없고(교체가 6~12배 늘어 오히려 같거나 느림) 탐색 결과도 같거나 약간 낮다 → **기본값으로 채택하지 않음.** 옵션(`search.startFrom = "INCUMBENT"`)으로만 남기고, 결과가 달라지므로 입력 지문에 들어간다.

## 3. 시간 예산·취소·best-so-far

엔진은 시계·난수를 쓰지 않는 순수 함수로 유지하고, 호출자가 `search`(`now`·`deadlineAt`·`maxEvaluations`·`isCancelled`)를 주입한다.

| 종료 사유 | 뜻 | 같은 입력이면 같은 결과? |
|---|---|---|
| CONVERGED | 더 좋아지는 교체·맞교환이 없음(국소 최적, **전역 최적 증명 아님**) | 예 |
| MAX_MOVES | 교체 횟수 상한 도달 | 예 |
| EVAL_BUDGET | 평가 횟수 예산 소진 | **예**(예산이 입력 지문에 들어감) |
| DEADLINE | 시간 마감 | 아니오(실행 환경에 따라 달라짐 — `reproducible=false`) |
| CANCELLED | 취소 | 아니오 |

**best-so-far가 항상 유효한 이유**: ① 구성 단계에서 정지 판정이 나면 남은 칸은 평가 없이 후보 단독 가치로 빠르게 채운다(제약·반복 한도는 그대로 확인). ② 국소탐색은 이동을 **평가하기 전에만** 정지 판정을 하고, 평가 중 이동은 항상 되돌리거나 채택한 상태로 끝난다. ③ 채택은 목적함수가 엄격히 좋아질 때뿐이라 탐색 직후 값 ≥ 구성 직후 값. ④ 시간 마감·취소 때는 대체 후보(Swap용) 계산을 생략하고(`alternativesSkipped`), 편성안과 제약 검증은 그대로 한다. 어떤 경우든 `validateEngineOutput`이 결과를 다시 확인한다(시험: 예산 0·취소·가짜 시계 마감 모두 하드 제약 위반 0, 칸 수·빈칸 수 동일).

**평가 예산별 탐색 직후 목적함수**(합성 세계 1, KEEP; 완주 584.08, 평가 약 75만 회):

| 평가 예산 | 탐색 직후 목적함수 | 시간 |
|---|---|---|
| 0(빠른 채움만) | 463.05 | 0.5초 |
| 2만 회 | 562.18 | 0.7초 |
| 10만 회 | 583.30 (완주의 99.87%) | 1.1초 |
| 30만 회 | 583.94 | 3.2초 |
| 60만 회 | 584.08 | 6.5초 |
| 무제한(완주) | 584.08 | 7.0초 |

이 합성 세계에서는 국소탐색이 구성 직후 대비 +0.15%만 더하면서 시간의 90%를 쓴다(그래서 예산을 줘도 손실이 작다). **일반화하지 않는다.** KEEP 모드의 최종 목적함수는 "차이가 작으면 지난주 편성 유지"(`keepInsignificant`) 때문에 의도적으로 탐색 직후 값보다 낮아질 수 있어, 보고서는 두 값(`objectiveAfterSearch`·`objectiveFinal`)을 따로 낸다.

**서버 연결(DB 변경 없음)**
- 러너: 요청 시작 기준 **45초**(`DEFAULT_SEARCH_DEADLINE_MS`, 환경변수 `IDEAL_SEARCH_DEADLINE_MS`로 조정)에 탐색을 마감하고 지금까지의 최선안을 낸다. 서버 함수 제한은 60초이므로 시간 초과로 아무것도 못 받는 대신 "탐색 중단(최선안)" 결과를 저장·표시한다.
- 취소: 브라우저가 연결을 끊거나 [계산 취소]를 누르면(`request.signal`) 엔진이 멈추고 **저장하지 않는다** — 이전에 저장된 유효 편성안이 그대로 남는다(HTTP 499).
- 백테스트는 마감·취소·예산으로 끝난 탐색을 **검증 자료로 쓰지 않고 거부**한다(조용히 섞이지 않게).
- 화면: 계산 중 **경과 시간만**(서버가 진행률을 알려 주지 않으므로 퍼센트를 만들지 않음)과 [계산 취소] 버튼, 취소·실패 시 "이전 편성안은 그대로입니다". 끝난 뒤 상태 띠가 종료 사유·평가 횟수·구성 직후 대비 개선을 알린다(수렴이 아니면 "탐색 중단(최선안)" 칩과 주의 문구).

## 4. job 분리 설계(미구현 — DB 변경이 필요해 승인 후)

지금은 동기 POST(≤60초)다. 실데이터가 커서 45초 마감에 자주 걸린다면 다음으로 분리한다.
- `ideal_schedule_jobs`(id, actor, **idempotency_key**(actor별 unique), params, status = QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELLED, stage, evaluations, best_objective, elapsed_ms, run_id, error, created_at/finished_at).
- idempotency: 같은 키의 재요청은 새 계산을 만들지 않고 기존 job을 돌려준다(더블클릭·새로고침·재시도 방지). 지금은 화면이 계산 중 버튼을 막는 것뿐이고 **서버 측 중복 방지는 없다**.
- 워커가 `search.isCancelled`에서 job 상태를 읽어 취소를 반영하고, 마감 도달 시 SUCCEEDED(탐색 중단 표시)로 저장한다. 화면은 job을 폴링해 **서버가 실제로 기록한 값**(단계·평가 횟수·현재 최선 목적함수·경과 시간)만 보여 준다 — 가짜 진행률 없음.
- 취소·실패·타임아웃이면 기존 저장 편성안은 건드리지 않는다.

## 5. 이전 단계(OPT03)에서 넘어온 항목

- T07 엔진 수준 차분 평가 = 전체 재평가 → **완료**(검증 모드, 불일치 0).
- T08 서로 다른 seed/시작에서 하드 제약 위반 0, 큰 문제 최적 보장 안 함 표시 → **소형 문제의 다중 시작(시드 12개)·엔진의 두 시작점(GREEDY·INCUMBENT) 모두 위반 0**, `searchKind=SEARCHED_BEST`("최적 증명 아님")·종료 사유 표시. 엔진 자체에는 다중 시작을 넣지 않았다(2절 사유).
- T10 시간 예산·취소 시 best-so-far, 이전 유효안 보존 → **완료**(예산 0·취소·마감 모두 유효, 취소는 저장하지 않음).

## 6. 남은 한계

- 모든 시간·격차는 합성 세계 값이다. 실데이터에서는 후보 풀·권리·제약이 달라 시간이 다를 수 있다(운영 실행의 `summary.search.phaseMs`로 확인).
- 소형 문제 비교의 연속 가산은 일부러 크게 넣은 구조라, 다중 시작·빔의 실제 이득은 실데이터로 확인해야 한다.
- 탐색은 최적을 증명하지 않는다(국소 최적). 5분 격자·순차 확정이라 더 나은 편성이 있을 수 있다.
- 기존 틀 유지 모드의 구성(탐욕)·유지 판단·대체 후보 계산은 중단 불가 구간이다(각각 0.4초·수 ms·0.3초 수준, 합성 기준). AI 모드의 DP(0.7~1초)도 중단하지 않는다.
- job 분리·서버 측 idempotency·실시간 진행(단계·평가 횟수)은 DB 변경이 필요해 구현하지 않았다.
- 마이그레이션 변경 없음. 모든 변경은 미커밋·미배포.
