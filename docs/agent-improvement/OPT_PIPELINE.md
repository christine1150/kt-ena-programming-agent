## 0. 한눈에 보는 결론

1. **개선율 = (이번 안 주간 기대 평균) ÷ (기준 주 CURRENT 주간 기대 평균) − 1** 이며 두 값 모두 같은 예측 모델이 낸 *기대값*이다(실적 대비가 아님). [재확인: `engine.ts:489-523, 626-679`]
2. **두 평균은 서로 다른 시간의 평균일 수 있다.** 기대값이 없는 방영(시청률 NULL·방영 기록 공백)은 평균에서 빠지는데, 이번 안은 일주일 전체가 채워지고 기준 주는 비는 곳이 생길 수 있다. 합성 실험에서 기준 주의 프라임 방영 기록이 절반 비면 **같은 시간 기준 +1.7%가 전체 평균 비교로는 +13.5%로 부풀었다**(비율 80%면 +24.3%). → **이번 단계에서 수정**: 개선율을 "두 편성 모두 평가값이 있는 같은 요일·분"만으로 다시 계산해 기본 표시로 쓰고, 시간 범위가 다르면 안내한다.
3. "+80%"류 큰 값의 정확한 원인은 **저장된 원시 값이 없어 복원하지 못했다**(§8). 후보 원인과 확인 방법(`scripts/opt01-run-audit.mts`)만 남긴다. 분모를 표시값으로 역산해 확정하지 않았다.
4. 예측 모델 자체의 낙관 편향은 합성 세계에서 **작거나 보수적**이었다: 진짜 차이가 없는 세계에서 보고 +1.6%(정답 0%), 진짜 차이가 있는 세계에서는 보고가 정답보다 훨씬 **작았다**(수축 때문). 즉 모델의 큰 개선율은 "고르면서 부풀려진 값"보다 **분모·시간 범위 같은 집계 조건**을 먼저 의심해야 한다. 단, 합성 세계는 모델이 맞는 구조라 실제 채널의 결과가 아니다(§9 한계).
5. 목적함수는 `value`(점수)이고 화면 보고값은 `expected`(예측)다. 기본 가중치(KPI 35%)는 **합성 세계에서 시청률 우선(KPI 100%)보다 정답 개선율이 1.3~2.0%p 낮았다**(타깃 구성비·안정성·연결 성분을 시청률로 환산하지 않기 때문). "요일×시·추세 성분 제외" 변형은 시청률 우선과 거의 같았다 — 중복 반영이 눈에 띄는 손해를 만들지는 않았다.
6. 수동 교체는 권리 판정을 거치지 않는다(`runStore.swapBlock`, 권리 코드 없음). 화면에 그 사실을 표시했고(단계 10), 코드 수정은 OPT06 첫 작업이다.

## 3. 기대 시청률 식 [재확인: `features.ts:100-261`]

기대값 `expected = idx × baseline(요일, 시)`

- **baseline**: 채널 평균 → 시 평균 → 요일×시 평균 순으로 같은 k(=4)로 수축. 학습 창(91일, 공휴일 제외) 안 모든 방영의 단순 평균이며 최근 가중은 없다.
- **idx**: `Σ(w·r) ÷ Σ(w·b)` — 방영별 시청률 r을 *그 방영이 있던 슬롯의 baseline b*로 나눈 비율의 가중합. 최근 28일 방영은 w=2, 나머지 1. 5개 단계 키(① 프로그램×방영유형+요일+시, ② +시, ③ 프로그램 전체, ④ 장르+요일+시, ⑤ 장르+시)를 구체→일반으로 수축: `idx_L = (n_L·idx_L + k·idx_{L+1}) / (n_L + k)`, ⑥ 채널 baseline(지수 1).
- **표본(근거 방송)**: `n_L`은 그 단계에 쌓인 방영 건수(가중 전). 시청자 패널 표본이 아니다 → 화면 라벨을 "표본"에서 **"근거 방송 N건"**으로 바꿨다(이번 단계).
- **신뢰도** = `min(1, 프로그램 자체 근거 방송 / 12) × 안정성`. 장르·채널 폴백은 신뢰도에 넣지 않는다.
- 폴백 단계: `minN`(기본 3) 이상 쌓인 첫 단계가 `fallbackLevel`; 없으면 6.

예(표본 크기 효과): k=4에서 근거 방송 3건이면 그 단계 지수의 영향은 3/(3+4)=43%, 8건이면 67%, 12건이면 75%. 근거 방송이 적을수록 지수는 일반 단계 쪽으로 끌려가 기대값은 슬롯 baseline에 가까워진다(보수적).

값 처리: 시청률 0은 유효 측정(평균에 포함), NULL은 제외(표본 건수에는 남음). 요일×시 적합도는 그 프로그램 전체 지수가 0 이하면 계산하지 않는다. [재확인: `features.ts:115-116, 213`]

## 4. 점수(목적함수)와 예측의 관계 [재확인: `scoring.ts:256-416`]

- 화면의 "주간 기대 시청률"은 `expected`의 분 가중 평균이다(Fit Score가 시청률로 둔갑하지 않음).
- **최적화는 `value`를 최대화한다**: `value = fitness × (1+전략보너스) × baseline × 분 × (1 − 패널티합)`, `fitness = Σw·c ÷ Σw`(근거 없는 성분은 분모에서 제외). 성분 c: kpi(=idx), target(타깃 구성비 지수), weekday_slot(요일×시 적합도), trend(최근4주÷12주, 0~2), stability(채널 중앙값 대비, 0~2), lead(앞뒤 관측 연관, 0~2). 패널티: 연속·같은 시 반복·장르 집중·저신뢰(최대 0.1)·길이 불일치, 합 상한 0.95.
- 따라서 **목적함수 1등 ≠ 기대 시청률 1등**일 수 있다. KPI 100% 설정에서는 `value = expected × 분 × (1−패널티)`가 된다.
- **중복 반영 후보**: 최근성은 `idx`(w=2)와 `trend` 두 곳, 요일×시 정보는 `idx` ①단계와 `weekday_slot` 두 곳에 들어간다. 타깃 구성비 `target`은 기대값에는 없고 fitness에만 들어간다(기대 시청률 보고에는 반영되지 않는 "점수" 요소). **[실험]**: 두 성분을 뺀 변형이 기본 가중치와 정답 개선율이 비슷(차이 ≤0.7%p)해 *중복이 가시적 손해를 만든다는 증거는 못 찾았다*. 효과 크기는 실제 데이터에서 다시 측정해야 한다.
- "시청률 우선"(KPI 100%)은 요일×시·최근성 정보를 약화시키지 않는다: 그 정보가 `expected()` 안(idx ①단계·최근 가중)에 이미 들어 있기 때문. 약화되는 것은 타깃 구성비·안정성·연결·반복 패널티의 영향이다. [코드 확인 + 실험]
- 순환 편성·반복 한도·Avail의 우선순위: Hard 제약(필수·잠금) → 권리 허용 슬롯 → 반복 한도(오리지널 예외) → 점수 최대화. 한도 위반 해소는 휴리스틱(최적성 보장 없음, L6). [단계00]

`wavg`는 `expected === null`인 블록을 분모에서 뺀다. [재확인: `engine.ts:494-505, 651-661`] 이번 안의 AI 모드는 빈 곳을 ≤10분만 허용해 거의 전체가 채워지고, 기준 주는 방영 기록이 없거나 시청률이 비면 그 분이 빠진다. 그래서 두 평균이 다른 시간 위에서 계산된다.

**수정(이번 단계):** `src/lib/idealSchedule/comparison.ts`의 `compareOnCommonSupport` — 두 편성 모두 `expected`가 있는 같은 (요일, 분)만으로 평균·개선율을 다시 계산, 평가 시간 차이·기존 전체 평균 비교와의 차이(%p)를 함께 반환. 화면의 개선율(편성표 제목·요약·모바일 막대)은 "같은 시간 기준 {기준 주} 대비 +x%"로 표시하고, 시간 범위가 다르면 상태 띠에 분 수와 영향 %p를 안내한다. 클라이언트가 저장된 블록에서 계산하므로 수동 교체 후에도 같은 값을 보인다. 테스트 `test:opt01` 20개, 변이 8종 모두 검출.

## 6. "기존 모델 검증" 버튼(백테스트) [재확인: `backtest.ts`, `backtest/route.ts`]

- `POST /api/scheduling/ideal-schedule/backtest`: 이미 지난 주 W에 대해 as_of = W−1로 **엔진 전체(최적화 포함)를 실행**하고, 실제 방영을 같은 모델로 평가한다. 시간 제한: 라우트 `maxDuration=60`, 여러 주는 `backtestRunId`로 묶어 순차 호출.
- **저장하는 것**: (a) `ideal_schedule_runs`/`blocks`에 *새 편성안*(saveRun), (b) `ideal_schedule_backtest_runs`(조건·config 스냅샷), (c) `ideal_schedule_backtest_results`(주별 실적 평균·기대 평균·보정 MAE/bias·방영별 detail). 즉 버튼을 누를 때마다 편성안 목록에 검증용 run이 쌓인다.
- **계산하는 것**: 실제 편성의 방영별 `기대 − 실측`(MAE, bias, 근거 등급 A/B/C별, 예상 범위 적중률, 상대 MAE, 이상적 편성 기대 − 실제 편성 기대 평균).
- **평가하지 않는 것**: 기준 모델(최근 평균 등)과의 비교, 추천 편성의 실제 성과(관측 불가), 구간의 *held-out* 적중률(범위는 *이전 주의 잔차*로 만들고 그 주 실측으로 적중률을 센다 — 시간 순서는 맞지만 비교 모델이 없다).
- **시간 누수 점검**: 데이터는 RPC가 `broadcast_date ≤ as_of`로 강제, 잔차는 `week_start ≤ as_of−6`만 사용(같은 주 중복 시 가장 최근 결과 하나). **그러나** 장르 맵·설정(config)·필수 편성 제약·직재방 규칙·업로드 편성표는 *현재 값*을 쓰고 `available_at` 관리가 없다(과거 주 검증이 오늘 수정된 값으로 재현됨 — OPT02에서 버전 관리). `req.weekStart >= today` 검사가 UTC 날짜라 월요일 00~09시 KST에 어긋날 수 있다.
- 재현: 순수 엔진 수준에서는 `opt01-trace.ts`가 같은 구조(as_of 이전 데이터만, 실제 주 평가)를 합성 데이터로 돌린다. 운영 생성/재계산은 실행하지 않았다.

## 8. 저장된 ENA Play 10/5~10/11 사례 (0.047/+80.2%, 0.048/+82.0%, 기준 9/14, 수동 수정)

**복원하지 못했다.** 저장된 run의 블록 원시 값은 운영 DB에만 있고 이 작업은 운영 DB를 읽지 않는다. 표시값(0.047, +80.2%)으로 분모를 역산해 확정하지 않았다. 코드에서 확인된 사실과 가설만 적는다.

- **기준 9/14 [코드 확인 + 달력]**: `pickCurrentWeek`는 대상 주 직전부터 최대 4주를 거슬러 *7일 데이터가 모두 있고 공휴일이 없는* 첫 주를 고른다. 2026-10-05 대상 주 직전의 9/28·9/21 주는 추석 연휴(9/24~9/26 근처)·개천절(10/3)이 있어 건너뛰고 3주 전 9/14 주가 선택됐을 가능성이 높다(공휴일 목록 확인 필요).
- **0.047 vs 0.048 [가설]**: (a) 수동 교체 후 재계산 전의 *클라이언트 재합산*(`weeklyExpected`)과 *저장 요약* 값이 달랐거나, (b) 재계산으로 새 run(`parent_run_id`)이 만들어져 값이 바뀌었을 가능성. 이전에는 화면 곳곳이 두 값을 섞어 썼다 — 단계 10에서 한 값(`shownExpected`)으로 통일했다. 어느 쪽인지는 run 두 개의 블록을 비교해야 알 수 있다.
- **+80%의 원인 후보 [가설, 확인 방법 포함]**: ① 분모 시간 범위 불일치(§5) — 기준 주의 프라임 방영 기록·시청률 공백, ② 기준 주가 평소보다 낮은 주(특집·측정 공백), ③ 필수 제약이 없는 AI 계획이 고성과 프로그램을 프라임에 모음, ④ 기대값이 작은 채널에서 분모가 작아 비율이 커짐(ENA Play는 0.026 안팎의 기준이면 절대 차이는 작다).
- **확인 방법**: 사용자가 `.env`가 있는 PC에서 `npx tsx --env-file=.env scripts/opt01-run-audit.mts <run_id>`를 실행하면 읽기 전용으로 분자·분모·평가 시간·공통 시간 개선율·needs_recalc·parent_run_id를 한 번에 보여 준다(두 revision의 run id 각각 실행해 비교).

## 9. 합성 세계 실험 [실험, `npm run opt01:trace`]

세계: 20개 프로그램, 24시간×7일 고정 편성표, 이력 12주, 방영별 로그정규 잡음 σ=0.25, 정답 = 잡음 없는 평균. 엔진은 운영과 같은 `runIdealScheduleEngine`(기본 설정, 경쟁사 없음, 제약 없음). 결과표(AI 시간 최적화, 세계 10~12개 평균; `정답`은 추천안과 기준 주의 진짜 평균 비율).

| 조건 | 보고 개선율 | 같은 시간 기준 | 정답 개선율 | 해석 |
|---|---|---|---|---|
| 프로그램 간 진짜 차이 없음(null) | +1.6% | +1.6% | 0.0% | 고르면서 생기는 부풀림 약 +1.6%p |
| 차이 σ=0.08 | 2.2% | 2.2% | 5.1% | 보고가 보수적 |
| 차이 σ=0.2 | 4.2% | 4.2% | 20.2% | 보수적(수축 + 새 슬롯은 근거 단계가 얕음) |
| 차이 σ=0.45 | 7.0% | 7.0% | 47.1% | 보수적 |
| 차이 σ=0.2 + 주별 변동 0.08 + 시간대 상호작용 0.3 | 6.8% | 6.8% | 37.9% | 모델이 모르는 구조가 있어도 보고가 정답보다 작음 |
| 차이 σ=0.2 + **기준 주 프라임 방영 50% 공백** | **15.6%** | **4.1%** | (전체 평균끼리) 33.7% | **집계 조건만으로 +11.5%p 부풀림** |
| 차이 0 + 기준 주 프라임 50% 공백 | 13.5% | 1.7% | – | 진짜 차이가 없어도 +11.8%p 부풀림 |

가중치 비교(정답 개선율, AI 모드): 기본 가중치 37.9% / 시청률 우선 39.9% / 슬롯·추세 성분 제외 38.5% (σ=0.2+변동+상호작용), 20.2% / 21.5% / 21.5% (σ=0.2).
KEEP_CURRENT 소요 시간: 이 세계(168칸, 프로그램 20개)에서 한 번 실행에 **31~44초**(AI 모드는 3~4초) — 서버 `maxDuration=60`에 근접(OPT04에서 다룬다).

**한계(정직하게):** 합성 세계의 모델 구조(프로그램×슬롯의 곱)는 엔진의 식과 같아 *모델이 맞는 세계*다. 실제 채널은 신규작·특집·재방 효과·경쟁 편성·휴일·권리 제약이 있어 낙관 편향이 더 클 수 있다. 위 수치는 "엔진 구조가 어떤 방향으로 어긋나는가"를 보는 용도이며 실제 채널의 개선율 보증이나 부정이 아니다. 실제 검증은 OPT05(시간순 검증)에서 한다.
